# Anthropic Managed Agents：把 Agent 的大脑和手解耦

## 背景

Anthropic 在 2026 年 4 月 8 日发布了工程文章 `Scaling Managed Agents: Decoupling the brain from the hands`。这篇文章不是在讲一个新模型有多强，而是在讲一个更长期的问题：

**当 Agent 开始运行长任务、接入私有环境、调用多个工具时，系统应该怎样设计，才能不被今天这版 harness 绑死。**

文中给出的核心拆分很清晰：

- `session`：保存事件日志和可恢复上下文
- `harness`：负责驱动模型循环和工具编排
- `sandbox / tools`：负责真正执行动作

Anthropic 把它概括成一句很工程化的话：把 Agent 的“脑子”和“手”拆开。

## 为什么重要

- **它给长任务 Agent 提供了比“一个大容器包一切”更稳的架构**：会话、调度、执行环境不再绑在同一个实例里，某一层挂掉不必整条任务一起丢。
- **它把安全边界前移成结构问题，而不是只靠权限提示**：如果模型生成的代码根本拿不到凭据，prompt injection 的破坏面就小很多。
- **它解释了为什么未来的 Agent 基建会越来越像分布式系统**：恢复、重试、状态持久化、隔离执行环境，这些已经不是附加功能，而是默认前提。

## 前端/AI 开发落地建议

### 1. 不要把 Agent 状态只放在“当前上下文”里

如果你在做前端 AI 工具、内部 Copilot 或多步自动化，最好显式区分：

- 用户可见会话
- 模型当前轮次上下文
- 持久化任务事件
- 工具执行结果

这样做的好处是：前端能展示任务恢复点，后端也能在中断后继续跑，而不是把所有信息都塞进一次性上下文窗口。

### 2. 把执行环境当成可替换资源，而不是 Agent 本体

Anthropic 的设计启发很直接：sandbox 应该像工具一样被调用，而不是和 orchestration 死绑。对团队自己的 Agent 系统来说，这意味着：

- 本地沙箱、远程容器、浏览器自动化都应该抽象成统一执行入口
- 失败要能重建环境，而不是人工进容器救火
- 不同任务可以按需接不同“手”，而不是每次都启动全套环境

### 3. 前端要把“任务状态机”展示出来

当 Agent 架构被拆成多层后，前端不能只显示一串聊天回复。更值得做的是显式展示：

- 当前是否在推理、取上下文还是调用工具
- 哪个 sandbox 正在执行
- 是否发生恢复、重试或切换环境
- 哪一步需要人工确认

这类可观测性会直接影响产品是否能进入真实工作流。

## 注意事项

- **不要把“解耦”理解成无成本**：接口一旦拆开，日志、追踪、重试协议和错误分类都要补齐。
- **会话持久化不等于上下文无限增长**：状态可以长期保存，但真正喂给模型的内容仍要做筛选和压缩。
- **统一工具接口很重要，但不要过度抽象**：抽象层太薄会泄露底层差异，太厚又会让能力受限，接口设计要围绕真实任务来定。
