# Responses API WebSocket 模式：Agent 延迟为什么能再降 40%

## 背景

OpenAI 在 2026 年 4 月 22 日发布了工程文章 `Speeding up agentic workflows with WebSockets in the Responses API`，拆解了一个很实际、也很容易被忽略的问题：

**当模型本身已经越来越快时，真正拖慢 Agent 的，开始变成工具循环外面的 API 开销。**

文章里提到，Codex 这类编码 Agent 在一次复杂任务里，会反复经历“模型决定动作、调用工具、把结果送回 API、继续下一轮”的循环。过去推理速度慢时，这些往返的服务开销还不显眼；但当更快的模型上线后，接口层和上下文重建成本就变成了瓶颈。

OpenAI 的做法是给 Responses API 增加 WebSocket 模式，用持久连接和连接内缓存，减少每轮都重新处理整段对话历史的成本。官方披露，最终让 agentic workflows 端到端提速最高可达 40%。

## 为什么重要

- **它提醒我们，Agent 体验问题不只是“模型够不够强”**：一旦工作流进入多轮工具调用，协议、缓存、连接模型和编排方式都会直接影响用户体感。
- **这对前端和全栈开发者很现实**：很多团队正在做 AI IDE、浏览器内 Agent、工作流自动化或带工具调用的 Web 应用，延迟往往比单轮问答更敏感。
- **它说明“保持 API 形状稳定”本身也是工程能力**：OpenAI 最终没有强迫开发者重写一套完全不同的交互模型，而是在 WebSocket 连接上继续保留 `response.create` 和 `previous_response_id` 的使用方式。

## 前端/AI 开发落地建议

### 1. 把 Agent 延迟拆成“模型时间”和“编排时间”分别观测

如果你在做带工具调用的 AI 应用，建议不要只盯模型输出速度。至少要分开看：

- 首 token 时间
- 每轮工具调用前后的等待时间
- 上下文重建或状态恢复开销
- 工具执行本身耗时

否则很容易误判成“模型太慢”，但真实瓶颈可能在接口编排或上下文重复处理。

### 2. 优先复用连接内状态，而不是每轮全量重放

OpenAI 这篇文章里最有价值的点，不只是用了 WebSocket，而是：

- 通过持久连接缓存前一轮 response 状态
- 只处理新增输入，而不是反复处理完整历史
- 复用工具定义、命名空间和部分采样产物

这对自建 Agent 后端也有参考价值。真正该优化的往往不是“把 HTTP 换成 WebSocket”本身，而是减少重复工作。

### 3. 前端接入时，把实时传输和审批边界一起设计

更快的 agent loop 会让应用显得更“即时”，但也更容易让危险操作连贯执行。工程上建议同步考虑：

- 哪些工具调用允许自动继续
- 哪些动作必须人工确认
- 前端如何展示中间状态、暂停点和工具结果

速度提升不应该以牺牲可控性为代价。

## 注意事项

- **WebSocket 不是万能解药**：如果你的瓶颈在工具执行、沙箱冷启动或外部 API，本地持久连接也帮不了太多。
- **不要只复制协议层做法，而忽略状态模型**：这篇文章最关键的是“连接作用域内缓存前序状态”，不是单纯换传输通道。
- **更快的 Agent 需要更好的可观测性**：轮转变快之后，如果没有足够的事件和日志，排查问题反而更难。
