# Context Engineering：AI Agent 为什么要少给上下文、按需取上下文

## 背景

Anthropic 在 2025 年 9 月 29 日发布了 `Effective context engineering for AI agents`。这篇文章值得反复看，因为它把很多团队对 Agent 失败的误判说透了：

很多问题并不是“提示词不够强”，而是**给模型的上下文组织方式本身就错了**。

文章把焦点从 prompt engineering 往前推了一层，强调真正关键的问题是：

**在每一轮推理里，什么信息应该进入上下文窗口，什么信息应该暂存、延后获取或直接丢弃。**

Anthropic 还明确提醒，context 是有限资源，随着 token 变多，模型会出现注意力退化和所谓的 `context rot`。

## 为什么重要

- **它改变了做 Agent 的优化方向**：从“怎么写一句更强的系统提示”转向“怎么维护一个高信噪比的上下文状态”。
- **它解释了长任务 Agent 为什么常常越跑越笨**：不是模型不会做，而是上下文越来越脏，历史消息、工具结果和无关细节把注意力预算吃掉了。
- **它对前端产品也有直接影响**：很多 AI UI 还在默认把全部历史消息原样塞给模型，但真正稳定的系统往往需要摘要、分层记忆和按需检索。

## 前端/AI 开发落地建议

### 1. 把上下文视为运行时资源，而不是聊天记录副本

如果你的产品有多轮任务、文件分析或工具调用，不要默认“会话历史 = 下轮上下文”。更稳的做法是拆成几层：

- 固定系统约束
- 当前任务目标
- 最近几轮关键交互
- 按需拉取的外部资料
- 可压缩的历史摘要

这会比无脑拼接全部消息稳定得多。

### 2. 前端和后端都要支持“按需取上下文”

真正成熟的 Agent 往往不是一次塞满所有信息，而是：

- 先给最小可行动上下文
- 需要时再检索文档、事件或工具结果
- 在关键节点生成阶段性摘要
- 对已经消费过的大块上下文做裁剪

这要求产品层和基建层都支持上下文分层，而不是把上下文当黑盒字符串。

### 3. 把“上下文质量”纳入调试面板

除了看 token 用量，更值得在调试界面里暴露：

- 当前上下文由哪些片段组成
- 哪些内容来自检索，哪些来自历史消息
- 哪些内容经过摘要或压缩
- 当前轮次为什么选择这些上下文

这样团队才能判断问题到底出在模型、工具，还是上下文工程。

## 注意事项

- **长上下文不是免费的能力**：上下文窗口更大，不代表可以无节制堆信息。
- **摘要有损，检索也会漏**：所以需要围绕真实任务设计验证点，而不是盲信压缩结果。
- **不要把 context engineering 只理解成 RAG**：它还包括消息裁剪、工具结果组织、记忆分层、状态回放等一整套运行时设计。
