# MDN MCP Server：把兼容性数据直接接入 AI 编码工作流

## 背景

MDN 团队在 2026 年 6 月 15 日发布了 `Introducing the MDN MCP server`，正式把 MDN 文档和浏览器兼容性数据通过 MCP 暴露给 AI Agent 和 IDE。

这件事表面上看只是“又一个 MCP Server”，但它背后的价值很实际：前端开发最怕 AI 生成代码时引用过时平台知识，而 MDN 恰好掌握了 Web 平台里最关键的两类一手信息：

- API 和语法文档
- 浏览器兼容性与 Baseline 相关数据

官方还给出了一个很有说服力的测试结论：在查询 `light-dark()`、`:buffering`、`shadowrootslotassignment`、Web Serial API 这些较新的平台能力时，接入 MDN MCP 的 Agent 在兼容性判断上明显更可靠，而且响应速度大约快一倍。

## 为什么重要

- **它把“查文档”前移成了生成阶段的能力**：过去我们是等 AI 产出代码后，再人工去 MDN 纠错；现在可以让工具在生成时直接拿到 MDN 的最新上下文。
- **它对前端比对多数通用知识库更有价值**：前端问题经常卡在“是否已可用”“是否跨浏览器稳定”“语法边界是什么”，这些恰好是 MDN 强项。
- **它会改变团队接入 AI 编码工具的默认基线**：以后评价一个前端 Agent，不只是看模型强不强，还要看它是否接入了可靠的平台知识源。

## 前端/AI 开发落地建议

### 1. 把 MDN MCP 当成前端 Agent 的基础设施

如果团队已经在用 Codex CLI、Claude Code、Cursor 或 VS Code Agent，就值得把 MDN MCP 作为默认接入项。它最适合覆盖这些问题：

- 某个新 CSS / Web API 到底能不能用
- 某个能力是否达到足够的浏览器覆盖
- AI 生成的实现是否混淆了旧规范和新规范

### 2. 把“平台知识校验”从人工 review 迁到工具链前面

更稳的做法不是只在 Code Review 里提醒“去查 MDN”，而是把流程改成：

- 生成代码时优先读取 MDN MCP
- 遇到新 API 时要求返回兼容性说明
- 对关键交互能力补充 Baseline 判断

这样能减少很多“代码能跑，但平台判断错了”的返工。

### 3. 和项目私有规范分层使用

MDN MCP 适合回答“Web 平台本身是什么状态”，但它不会替你决定：

- 你的业务最低兼容范围
- 是否允许实验性能力上线
- 设计系统是否允许某种交互写法

更适合的方式是：让 MDN MCP 负责平台事实，让团队规范负责上线策略。

## 注意事项

- **它目前还是 experimental**：官方明确说明当前阶段仍属实验期，接入前要评估数据处理和稳定性。
- **MCP 不能替代真实测试**：兼容性数据能提升方向正确率，但不能替代跨浏览器验证、可访问性检查和性能测试。
- **不要把它理解成“万能前端助手”**：它更像高质量事实源，而不是完整工程决策器。
