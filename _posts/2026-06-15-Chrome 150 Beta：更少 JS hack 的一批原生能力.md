# Chrome 150 Beta：更少 JS hack 的一批原生能力

## 背景

Chrome for Developers 在 2026 年 6 月 3 日发布了 `Chrome 150 beta`。这类 Beta 公告常常很长，但这次对前端尤其值得看，因为里面不是单点的小修小补，而是一批会直接影响日常组件实现方式的原生能力。

官方列出的更新里，比较值得前端团队提前关注的包括：

- `text-fit`：让文本原生适配容器宽度
- `focusgroup`：给复合组件提供声明式键盘导航
- `programmatic scroll promises`：让程序化滚动终于有可靠完成信号
- `out-of-order streaming`：支持不依赖 JavaScript 的乱序 HTML 流式更新
- `IndexedDB` 切到 `SQLite` 后端：提升可靠性

如果把这些点放在一起看，会发现 Chrome 正在继续把很多“以前只能靠 JavaScript 桥接”的能力，逐步下放到平台层。

## 为什么重要

- **可以少写一批脆弱的交互性 hack**：像键盘导航、文本自适应、平滑滚动完成检测，这些能力过去常常要靠额外脚本拼出来，维护成本高、边界多。
- **更适合和现代服务端渲染配合**：`out-of-order streaming` 这种能力不是小优化，而是直接影响未来 HTML 流式更新的工程模型，尤其适合组件化 SSR 和 AI 生成内容场景。
- **浏览器原生能力越强，AI 生成代码越不容易走偏**：很多 AI 代码之所以啰嗦，不是模型故意复杂，而是平台过去缺少更直接的表达方式。原生能力补齐后，生成结果也更容易更短、更稳。

## 前端/AI 开发落地建议

### 1. 优先盘点“能否删掉一层 JS”的组件

可以先从这些场景入手：

- 自适应标题和数字看板
- Toolbar、Tab、菜单组之类的复合控件
- 依赖滚动结束事件的吸顶、目录联动和导航定位

如果一个组件当前主要复杂度来自“为了补平台空白”，那就值得关注 Chrome 150 相关能力是否能逐步替代旧实现。

### 2. 把新能力纳入渐进增强，而不是一次性重写

像 `text-fit`、`focusgroup`、滚动 Promise 这类能力，比较适合作为增强层接入，而不是要求所有浏览器立刻一致。工程上建议：

- 先在非核心页面或内部系统试点
- 明确保留旧实现的降级路径
- 在设计系统层面封装能力开关，而不是散落在业务组件里

### 3. 给 AI 编码工具补充“优先原生平台能力”的约束

如果你在用 AI 生成前端代码，建议把以下原则写进项目提示词或工程规范：

- 能用原生 HTML / CSS / Web API 的，优先不用自定义脚本模拟
- 新能力默认以渐进增强方式接入
- 需要兼容性判断时，结合 Baseline 或目标浏览器矩阵决定是否启用

这样可以减少 AI 输出一堆看似通用、实际维护成本很高的历史方案。

## 注意事项

- **Beta 不等于已经可以无条件上生产**：它更适合提前评估实现方向，而不是立刻删掉所有旧逻辑。
- **不要把单个新特性孤立看待**：这次更重要的是趋势，平台在持续吞掉过去需要 JS 补位的交互层。
- **`out-of-order streaming` 这类能力要谨慎评估框架集成方式**：它很强，但一旦和现有 SSR/流式渲染链路耦合，就不只是“加一个 API”那么简单。
